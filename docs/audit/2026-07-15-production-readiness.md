## 1. Резюме

Проект представляет собой модульный монолит на Next.js 15, React 19, TypeScript, Prisma/PostgreSQL и Tailwind CSS. Расчётная логика в основном отделена от UI, присутствуют начальные unit-тесты, динамические metadata, sitemap, robots и административный интерфейс.

Публичный запуск в текущем состоянии заблокирован:

- production build не проходит;
- линтер не запускается;
- один unit-тест падает;
- в production-зависимостях есть critical/high уязвимости;
- настроенная PostgreSQL недоступна;
- публичные страницы зависят от БД и скрывают её ошибки как пустой ответ или 404;
- домен показывает страницу FastPanel и использует недоверенный TLS-сертификат;
- каталог содержит только пять калькуляторов, четыре из которых почти не имеют полезного поискового контента;
- существующая админка и хранение произвольного HTML/JSON-LD создают риски безопасности;
- в репозитории не обнаружены CI/CD, эксплуатационная документация baseline и настройки мониторинга Calculandia;
- текущие тесты не выявляют несколько подтверждённых ошибок в формулах и календарной семантике.

Предыдущая оценка 7–10 дней отменена как необоснованная. После декомпозиции expected critical path составляет 12–18 рабочих дней при параллельных потоках и доступном production-контуре; optimistic 8–10, pessimistic 20–30. Quality gates важнее календарной оценки. Подробности находятся в целевой архитектуре.

### 4.1 Конкретные ошибки

1. `app/api/calculators/[id]/route.ts`: несовместимость типов JSDOM `Window` и ожидаемого DOMPurify window.
2. `vitest.config.ts`: используется неподдерживаемая опция coverage `reports`; ожидается корректная конфигурация reporter.
3. `safeJsonParse(123 as string, 'fallback')` возвращает `123`, хотя тест и контракт ожидают fallback для значения неверного типа.
4. ESLint config присутствует, но сам ESLint отсутствует в зависимостях.

### 4.3 Аудит корректности расчётов

Независимое ревью показало, что зелёный статус существующих formula tests не является доказательством правильности. Подтверждены:

1. **Дни и рабочие дни.** Компонент не использует holiday API; локальный hardcode не знает ежегодные переносы и рабочие субботы. Inclusive/exclusive iteration даёт неверное количество рабочих дней для части интервалов.
2. **Календарное прибавление.** `31.01.2024 + 1 месяц` превращается в `02.03.2024`, а `29.02.2024 + 1 год` — в `01.03.2025`; month-end policy не определена.
3. **Timezone.** Парсинг `YYYY-MM-DD` через UTC может показать предыдущую локальную дату в западных часовых поясах.
4. **Процентная разница.** Симметричная разница отрицательных значений может быть отрицательной, а формула в UI расходится с реализацией для отрицательной базы.
5. **Дроби.** `-2 1/3` превращается в `-5/3` вместо `-7/3`; proper negative fraction может потерять знак при mixed rendering; UI допускает decimals при integer GCD algorithm.
6. **Системы уравнений.** Newton/random restart не гарантирует полноту или сходимость, выполняется синхронно при вводе и не ограничивает сложность.

Эти дефекты являются P0 для любого индексируемого URL. Принято: solver и рабочие дни исключаются из launch; остальные модули получают формальные domains, golden cases, tolerance и независимое review по [`../product/calculator-quality-standard.md`](../product/calculator-quality-standard.md).

## 5. Домен и фактический публичный сайт

Подтверждено на дату проверки:

- `calculandia.ru` и `www.calculandia.ru` разрешаются в `203.0.113.20`;
- сервер отвечает через nginx/FastPanel;
- в браузере отображается стандартная страница FastPanel, а не Calculandia;
- обычная HTTPS-проверка завершается ошибкой доверия к самоподписанному сертификату;
- при отключении проверки сертификата сервер отвечает HTTP 200;
- canonical redirect между `www` и основным доменом не подтверждён.

Следствие: поисковый робот сейчас не видит приложение, а публичный домен нельзя считать production-средой.

## 6. Данные и отказоустойчивость

### 6.1 Текущее состояние

- Актуальная Prisma schema настроена на PostgreSQL.
- В репозитории присутствует старый SQLite-файл `prisma/calculandia.db`, не соответствующий текущей архитектуре и содержащий устаревшие данные.
- Локально настроенная через `DATABASE_URL` PostgreSQL отклоняет аутентификацию; отдельная production-БД не проверялась.
- `lib/db-helpers.ts` перехватывает ошибки и возвращает пустые коллекции или `null`.
- Главная и страницы калькуляторов используют ISR/revalidation.

### 6.2 Риск

Временная недоступность БД может сформировать:

- пустую главную с HTTP 200;
- ложный 404 для существующего калькулятора;
- кэширование ошибочного состояния на время revalidate.

Для публичного SEO-каталога это неприемлемо. ADR-0001 принимает однозначное решение: первый релиз собирается из типизированных version-controlled definitions и не использует runtime-БД.

### 6.3 Недостатки модели

- `Calculator.category` — строка без внешнего ключа;
- нет явных `published/draft`, порядка сортировки, featured, версии формулы, автора и проверяющего;
- JSON-данные хранятся строками;
- `component` — произвольная строка;
- отсутствует audit log изменений;
- `RuHoliday.year` не имеет необходимого индекса;
- `updatedAt` не доходит до публичного DTO и не может корректно питать sitemap/индикатор свежести.

## 7. SEO-аудит

### 7.1 Что уже есть

- Next Metadata API;
- динамические title и description;
- canonical для страниц калькуляторов;
- Open Graph/Twitter metadata;
- `robots.ts` и `sitemap.ts`;
- условная генерация JSON-LD BreadcrumbList и дополнительного JSON-LD;
- FAQ-компонент;
- серверный рендер/ISR.

### 7.2 Критические проблемы

1. Видимый breadcrumb отображается plain text, а условный JSON-LD BreadcrumbList формирует category URL вида `/calculator/{category}`, ведущий на 404, когда schema включена.
2. Названия категорий в навигации не являются ссылками.
3. Нет общего каталога, поиска и task-based навигации.
4. Нет страниц доверия: методологии, источников, редакционной политики, контактов.
5. `sitemap.ts` присваивает всем URL текущую дату вместо реального времени существенного изменения.
6. В sitemap отсутствуют категории, потому что таких маршрутов нет.
7. Админка позволяет добавлять произвольный JSON-LD, который может не соответствовать видимому содержимому.
8. FAQPage и HowTo используются как потенциальные SEO-функции, хотя Google удалил FAQ rich results в мае 2026 года, а HowTo ранее был выведен из эксплуатации.
9. Root metadata остаётся общей и не формирует полноценную уникальную главную страницу.
10. Meta keywords занимают заметное место в админке. Google их игнорирует; Яндекс допускает влияние, но это не приоритет по сравнению с содержанием и выполнением задачи.
11. Четыре из пяти страниц слишком тонкие для конкурентного поискового результата.

### 7.3 Требуемое исправление

- реальные category hubs и breadcrumbs;
- уникальный intent и полезный контент каждой страницы;
- формулы, примеры, ограничения, источники и дата проверки;
- только типизированная structured data, отражающая видимую страницу;
- фактический `lastModified`;
- submit sitemap в Яндекс Вебмастер и Google Search Console после запуска;
- отсутствие массово сгенерированных тонких страниц.

## 8. Безопасность

### 8.1 P0-риски

- fallback `ADMIN_USER=admin` и `ADMIN_PASS=admin`;
- development fallback для `SESSION_SECRET`;
- нет throttling/lockout для административного логина;
- защита админки полагается на middleware при уязвимой версии Next.js;
- сохранение и вывод произвольного HTML;
- рекламный sanitizer разрешает `script` и `iframe`;
- дополнительный JSON-LD вставляется в script без экранирования `<`, что допускает stored script-breakout при компрометации админки;
- CSP дублируется в `next.config.ts` и `middleware.ts` и имеет разные правила;
- текущая CSP допускает широкие `unsafe-inline`, `unsafe-eval`, HTTP/HTTPS-источники;
- in-memory rate limiter не работает глобально между несколькими процессами;
- endpoint праздников позволяет инициировать внешнее получение и bulk write для широкого диапазона лет.

### 8.2 Решение для первого релиза

- отключить административный маршрут и write API в production;
- удалить fallback credentials/secrets и валидировать env при старте;
- исключить произвольные script/iframe/JSON-LD;
- использовать одну статически совместимую CSP;
- не переходить на nonce-CSP без осознанного отказа от ISR/CDN-кэширования: Next.js переводит nonce-страницы в динамический рендер;
- добавить rate limit логина на общем хранилище при возвращении админки;
- обновить уязвимые зависимости.

Источник: [Next.js Content Security Policy](https://nextjs.org/docs/app/guides/content-security-policy).

## 9. Производительность и наблюдаемость

## 11. UX/UI: краткое заключение

Подробный визуальный разбор находится в соседнем документе исследования.

Текущий UI визуально не ломается на проверенных ширинах, но:

- выглядит как служебный прототип;
- не имеет поиска и сильной главной страницы;
- на мобильном форма и рекламные блоки отодвигают результат;
- на десктопе пустой сайдбар расходует ширину;
- дефолтные значения часто являются placeholders, поэтому нет мгновенного результата;
- отсутствуют заметные trust-сигналы, примеры и связанные задачи.

## 12. Приоритеты исправления

### P0 — до любого публичного запуска

- валидный TLS, vhost и canonical redirect;
- обновление уязвимых зависимостей;

## 13. Критерий допуска к запуску

Запуск разрешён только если одновременно выполнены:

- test, typecheck, lint и build завершаются с кодом 0;
- нет unresolved reachable critical-уязвимостей; high исправлены либо имеют exception с owner, compensating control и expiry;
- домен отдаёт приложение по валидному HTTPS;
- `www` и HTTP имеют один постоянный canonical redirect;
- страница доступна без БД-ошибки и не превращает сбой в ложный 404;
- 14 из 14 manifest-страниц проходят измеримый page DoD;
- robots/sitemap/canonical проверены на production URL;
- пройдены smoke-тесты на 360, 390, 768, 1366, 1440 и 1920 px;
- доставлен test uptime/error alert; rollback drill выполнен ≤10 минут; mutable launch data отсутствуют.

Полный измеримый release DoD является нормативным в [`../architecture/production-target-and-roadmap.md`](../architecture/production-target-and-roadmap.md), разделы 14–15.
